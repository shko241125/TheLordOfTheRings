# 모리아의 그림자 — Three.js 3D 액션 어드벤처 구현 계획서

Sep 28, 2026 · @gosh

## TL;DR

**모리아 광산을 5개 구역으로 나눈 3인칭 실시간 핵앤슬래시 던전 크롤러다. 재미의 핵심은 빛·소리·물리·결정성을 게임 규칙으로 쓰는 새 아이디어 8개이며, 모두 공용 기둥 세 개(감지 필드·긴장도 디렉터·결정적 코어) 위에 선다.** 수직 슬라이스는 6주, 발로그까지의 풀 캠페인(약 3\~4시간)은 20주가 목표다. 기술 기준은 three.js r186(WebGPU + WebGL2 폴백), Rapier 0.21, navcat, Cloudflare Pages + Workers다(2026-09 조사).

TRIZ로 만든 아이디어 9개 중 플레이 감각을 가장 크게 바꾸는 네 가지(자세히는 4\~6장):

- **빛의 도박**: 어둠에 있을수록 치명타·전리품이 좋아지고, 빛에 있을수록 안전하지만 적이 모인다. 횃불이 시야이자 미끼다.
- **북소리 디렉터**: Left 4 Dead식 긴장도 디렉터의 상태가 곧 북소리 BPM이다. 플레이어는 귀로 다음 웨이브를 예측한다.
- **고블린 물결**: 최대 200마리가 밀려오지만 가까운 8마리만 '진짜' AI다. 금 간 기둥을 무너뜨려 한 번에 막는다.
- **마자르불의 책**: 결정적 시뮬레이션이라 죽음·명장면을 수십 KB 입력 로그로 공유하고, 받는 브라우저가 다시 그린다.

## 2. 게임 컨셉과 핵심 루프

**한 줄 컨셉: "빛을 들고 어둠 속으로 들어가, 북소리가 다가오기 전에 나온다."** 가제는 \*모리아의 그림자(Shadow of Moria)\*이며, 하나의 구역은 약 15분 분량의 루프 한 바퀴다.

&#91;embedded content: 핵심 루프 · 5단계, 1사이클 약 15분\]

루프는 구역마다 돌지만, 강화는 언제나 등불(체크포인트)에서만 일어난다. 등불이 저장·상점·대장간·동료 대화의 거점이다.

### 차별화 아이디어

초안의 차별화 아이디어는 4\~6장으로 흡수됐다. '빛과 어둠'과 '스팅 경보'는 A 빛의 도박에, '북소리 긴장도'는 C 북소리 디렉터에, '사망 = 재접근'은 F 마자르불의 책에 들어갔다. '사진 모드'는 리플레이 공유가 그 역할을 더 싸게 해서 뺐다. '동료 호출'은 그대로 두고 9장(전투)에 정리했다.

## 3. 최신 핵심 기술 후보 조사 (2026-09 기준)

**23개 키워드를 조사해 채택 13, 선택(업그레이드) 5, 보류 5로 나눴다.** 기준은 "PC 브라우저 대부분에서 돌고, 그 기술이 있어야만 가능한 재미가 있는가"다. 예뻐지기만 하거나 빨라지기만 하는 기술은 후순위로 두었다.

이전 초안에서 바뀐 사실 세 가지:

- Three.js 최신은 **r186**(2026-09-24)이다. r183에서 `PostProcessing`이 \*\*`RenderPipeline`\*\*으로 이름이 바뀌었고, r185에서 `TiledLighting`이 제거되고 **`ClusteredLighting`**(Forward+)으로 대체됐다. 버전은 `three@0.186.x`로 고정한다.
- Rapier는 **0.21.0**(2026-09-25)이고, 저장소가 `dimforge/rapier`로 합쳐졌다. 동일 생성 순서를 지키면 WASM 빌드는 플랫폼 간 결정적이고 `takeSnapshot()`/`restoreSnapshot()`을 지원한다.
- WebGPU는 전 세계 약 \*\*87%\*\*가 쓸 수 있다. 다만 Firefox Linux·Android는 아직 Nightly뿐이라 WebGL2 폴백은 여전히 필수다.

## 4. TRIZ 아이디어 생성

**재미를 가로막는 모순 9개를 정의하고, 모순마다 TRIZ 발명 원리를 적용해 기술 키워드를 조합했다. 그 결과 아이디어 9개가 나왔다.** 목표 상태(IFR, 이상적 최종 결과)는 "재미가 이미 있는 자원 — 빛, 소리, 물리, 결정성 — 에서 저절로 생긴다"로 두었다. 새 시스템을 만들기보다 기존 시스템에 역할을 하나 더 주는 아이디어를 우선했다.

사용한 도구:

- **기술적 모순**: A를 개선하면 B가 나빠진다 → 40가지 발명 원리 중 해당 원리 적용.
- **물리적 모순**: 하나의 값이 동시에 +P이자 −P여야 한다 → 분리 원리(시간·공간·조건·규모).
- **SIT 5템플릿**: 벨기(빼기), 고곱(더하기), 나누기, 과제 통합(결합), 속성 의존(연동). 요청하신 "조합·결합·더하기·빼기"에 거의 그대로 대응한다.

### 2차 검토에서 바뀐 결정

- **F 공유 방식**: 처음에는 압축한 입력 로그를 URL에 담으려 했다. 체크포인트부터 다시 재생하려면 수 분치 입력이 필요해 URL 길이를 넘는다. 그래서 블롭(≤ 64KB)은 Durable Object에 두고 링크에는 ID만 담는다.
- **C 북소리**: 처음에는 체류 시간만으로 긴장을 올렸다. 그러면 탐험을 열심히 할수록 벌받는 구조가 된다. L4D처럼 "플레이어 긴장도" 기반으로 바꿈다.
- **B와 A의 결합**: LOD 전환의 튀는 문제를 어둠이 가려준다. 두 아이디어가 서로의 비용을 낮춘다(TRIZ 22 전화위복).

### 기둥 1 — 감지 필드 (A·B·D)

모든 적과 플레이어 보상 계산이 같은 두 함수를 쓴다: "이 지점은 얼마나 밝은가"와 "이 지점에 들리는 소음은 얼마인가". 렌더러의 광원 목록을 그대로 재사용하므로 "보이는 빛 = 규칙의 빛"이 보장된다.

```ts
// gameplay/perception.ts — 시뮬레이션 틱(60Hz)에서만 호출
export function lightAt(p: Vec3, lights: readonly SimLight[]): number {
  let lux = 0;
  for (const l of lights) {
    const d2 = distSq(l.pos, p);
    if (d2 < l.range2) lux += l.intensity * (1 - d2 / l.range2); // 렌더러의 감쇠를 단순 근사
  }
  return Math.min(1, lux);
}

export function noiseAt(p: Vec3, events: readonly NoiseEvent[], tick: number): number {
  let n = 0;
  for (const e of events) {
    const age = tick - e.tick;
    if (age < e.ttl && distSq(e.pos, p) < e.radius2) n = Math.max(n, e.loudness * (1 - age / e.ttl));
  }
  return n;
}

// 적의 감지 = 밝기 × 시야각 × 거리 + 소음. 시선 레이캐스트는 T0·T1 적에게만.
export const detect = (e: Enemy, target: Vec3, w: World) =>
  lightAt(target, w.lights) * fov(e, target) * falloff(e, target) + noiseAt(e.pos, w.noise, w.tick);
```

- **A 빛의 도박**
  - 치명타 배율 `1 + 0.5 × (1 − lightAt(player))`. 전리품 등급 상승 확률은 그 전투에서 어둠 속에 있던 시간 비율로 정한다.
  - 횃불은 F키로 들기·내려놓기·던지기. 던진 횃불은 Rapier 막대(상자) 강체 + PointLight 풀(최대 6, 40초 후 꺼짐).
  - 광원 예산: WebGPU는 ClusteredLighting 64개, WebGL2 폴백은 가까운 횃불 6개로 광원 풀을 재배치한다(M0 구현). 그림자는 플레이어 횃불 1개만.
  - 고블린은 빛을 싫어해 밝은 곳으로 들어오기 전에 멈칫한다. 트롤·우루크는 빛에 끌린다. 같은 값에 반대로 반응하게 해 선택을 만든다(TRIZ 13).
- **D 돌의 감각**
  - 키 하나로 발동, 쿨다운 8초. 반경 20m(드워프 30m) 음파가 1초에 퍼지고 2초간 유지된다.
  - TSL 후처리 노드: 깊이 버퍼로 월드 위치를 복원하고, `|dist − radius(t)|`에 smoothstep을 걸어 링을 그린다. 깊이 기울기로 윤곽선을 강조한다. TSL이라 WebGL2에서도 같은 코드가 돈다.
  - 발동 시 `NoiseEvent(radius 15m, ttl 3s)`를 발행한다. 적은 이동 중(속도 > 0.5m/s)일 때만 윤곽이 드러난다.
  - 접근성: 펄스 밝기·속도 옵션, 화면 전체 섬광 없음.

### 기둥 2 — 긴장도 디렉터 (C·B·E)

Left 4 Dead 방식의 플레이어 긴장도를 그대로 쓰되, 그 값을 **북소리로 들리게** 한다. 보이지 않는 디렉터가 들리는 디렉터가 되면, 플레이어는 조종당한다고 느끼는 대신 예측하고 대비한다.

| 상태 | 진입 조건 | 스폰 | 북소리 | 진동(패드) |
| --- | --- | --- | --- | --- |
| Relax | Fade 종료 | 없음(30\~45초 보장) | 없음, 바람·물방울 | 없음 |
| BuildUp | Relax 종료 | 소규모 순찰 | 60 → 90 BPM, 멀리서 | 매 4박 약하게 |

| Fade | Peak 3\~5초 유지 후 | 신규 스폰 중단 | 감속 | 없음 |

- 긴장도: 피격 +(피해/최대체력), 5m 안 처치 +0.05, 주변 15m에 적이 없으면 초당 5% 감쇠.

- 스폰 위치·규모의 변동은 시드 난수로만 뽑는다. F의 리플레이가 같은 웨이브를 재현하려면 필수다.
- **E 붕괴 지점**은 디렉터가 물결 경로를 고를 때 선호도를 준다. 물결이 금 간 기둥 옆을 지나가게 해 "한 방"의 기회를 연출한다.

| T1 무리 | 40 / 16 | navcat 경로 + 결정적 분리 조향 (crowd는 Math.sin/cos를 써서 미사용) | 원형 분리만, 토큰 대기 | 스키닝 인스턴싱 |
| T2 물결 | 나머지 (총 200 / 60) | 플로 필드(2Hz 갱신), WebGPU는 TSL 컴퓨트 | 없음. 광역(붕괴·화염·동료 호출)으로만 죽음 | 인스턴싱, 애니메이션 시간 오프셋 |

승격·강등은 거리와 `lightAt`으로 판단하고, 어두운 곳에서만 바꾼다. WebGL2에서는 컴퓨트 대신 CPU로 돌리고 T2를 60으로 제한한다.

**E 무너지는 모리아**

- Blender에서 `_frac` 접미사로 조각 5\~8개를 미리 나눠 둔다. 런타임 파색(Voronoi)은 하지 않는다.
- 내구도가 0이 되면 조각을 Rapier dynamic으로 전환한다. 붕괴 부피에 걸린 T2는 즉사, T0·T1은 큰 피해를 받는다.
- 5초 뒤 sleep하면 조각을 정적 메시로 병합하고, navcat 해당 타일만 다시 굽는다.
- 레벨 검사 스크립트: 주 동선 그래프에서 붕괴 지점을 끊어도 출구까지 가는 경로가 남는지 빌드 때 확인한다.

### 기둥 3 — 결정적 코어 (F·G·H)

"같은 시작 상태 + 같은 입력 → 같은 결과"를 지키면 리플레이·핏자국·시드 던전이 모두 입력 로그 하나로 해결된다. 버그 제보도 리플레이 파일 한 개로 재현된다.

결정성 규칙(코드 리뷰 체크리스트):

1. 게임 로직은 고정 60Hz 틱 안에서만 돌고 `dt`는 항상 1/60이다.
2. `Math.random` 금지 — 시스템별 시드 난수(mulberry32 등)를 쓴다.
3. 시뮬레이션에서 `Math.sin/cos/atan2` 대신 미리 만든 표를 쓴다. Rapier 문서가 플랫폼 차이의 원인으로 지목한다.
4. 엔티티 순회·Rapier 바디 생성 순서를 ID 순으로 고정한다. 비동기 로딩이 끝난 순서에 의존하지 않는다.
5. 히트박스는 AnimationMixer 시간이 아니라 시뮬레이션 틱으로 계산한 공격 진행도에서 나온다.

```ts
// save/replay.ts
type Replay = {
  v: 1;
  build: string;        // 빌드 해시: 다르면 재생 대신 요약 화면
  zone: string;
  start: SaveState;     // 마지막 등불 또는 2분 자동 경량 체크포인트
  seed: number;
  inputs: Uint8Array;   // 틱당 6바이트: 버튼 u16, 이동 i8×2, 카메라 yaw i16 (틱 간 델타)
};
// 보관·전송 시 CompressionStream('deflate-raw'), 로컬은 OPFS
```

- **F 마자르불의 책**: 죽음 화면에 "마지막 60초 보기"(자유 카메라, 0.25× 슬로우). 죽음은 발린 원정대의 기록 문체로 한 줄 기록된다(템플릿 40종 + 적·장소·무기 치환). 죽을 때마다 책이 두꺼워지는 Hades식 "죽음 = 진행"이다.
- **공유**: 블롭을 Durable Object에 올리고 `/r/<id>` 링크를 받는다. 받은 쪽 브라우저가 구역을 불러와 다시 시뮬레이션한다. 영상 인코딩 비용이 0이다.
- **G 룬 메시지·핏자국**: Worker + 구역별 Durable Object 1개. API는 `POST /rune {zone, pos, template, words}`, `GET /runes?zone=`, `POST /vote`, `POST /stain {zone, pos, replay5s}`. 문구 템플릿 예: "앞에 {적}", "{방향}으로 가라", "{물건} 있음", "횃불을 끄어라". IP 해시당 분당 요청 제한. 오프라인이면 기능만 숨겨지고 게임은 그대로 완결된다.
- **H 깊은 갱도(1.1)**: 시드 = `hash(YYYY-MM-DD)`. 순환 템플릿 6종으로 방 그래프를 만들고, 모듈러 키트로 방을 조립하고, WFC로 장식한다. 순위표 제출은 리플레이를 함께 올려 서버가 재생 검증할 수 있다(부정 방지).

**결정성 회귀 테스트(필수)**: Node에서 `@dimforge/rapier3d-compat`으로 렌더러 없이 고정 입력 로그를 두 번 돌리고, 60틱마다 상태 해시가 일치하는지 비교한다. CI에서 매 커밋 실행하고, 하나라도 어긋나면 F·G·H가 모두 깨진 것이다.

### I 두린의 문 (독립 연출)

- 문 앞에서 비문(자체 번역문)이 뜨고 입력창이 열린다. 입력은 NFKC 정규화·소문자화 후 정답 목록(`mellon`, `friend`, `친구`)과 편집 거리가 ⌊답 길이/4⌋ 이하이면 통과한다(여섯 글자 답은 오타 1개, 두 글자 답은 정확히 — 18장 M2-B).
- `SpeechRecognition`이 있고 `processLocally`가 가능하면 마이크 버튼을 보여준다. 없으면 버튼만 숨긴다. 클라우드 인식은 쓰지 않는다.
- 60초 동안 못 풀면 간달프가 힌트를 준다(원작 장면의 오마주).

## 7. 스토리·세계관·퀘스트

**플레이어는 발린의 모리아 재건 원정대(제3시대 2989년)의 유일한 생존자로, 30년 뒤 원정대가 모리아에 들어오기 직전 서문(호린 성문)에서 깨어난다.** 원작 사건(문의 감시자, 마자르불의 무덤, 크새드두의 다리)은 바꾸지 않고, 플레이어는 그 틈새에서 원정대의 길을 여는 '보이지 않는 조력자'다. 원작 캐놤을 건드리지 않는 이 구조가 팬층 반발을 가장 줄이는 선택이다.

- **동기**: 발린의 마지막 기록물(마자르불의 책) 조각 12개를 모아 동료들의 운명을 밝힌다. 조각은 메인·사이드 퀘스트에 분산된 수집형 로어다.
- **결말**: 크새드두의 다리에서 발로그와 싸우고, 간달프가 다리를 부수는 원작 장면으로 이어진다. 플레이어는 원정대의 후퇴를 엄호하고 동문으로 빠져나간다.

## 8. 캐릭터·성장·NPC

**클래스는 3종, 최대 레벨 20, 스킬 트리는 클래스당 3갈래 × 5단계 × 단계당 3노드(총 45노드)다.** 스킬 포인트는 레벨당 1개라 20레벨에서도 트리 한 갈래를 끝까지 찍고 나머지를 조금씩만 찍게 된다. 이 '부족함'이 빌드 선택과 다회차의 동기다. 스킬 초기화는 등불에서 무료로 허용한다(실험을 벌주하지 않는다).

| 클래스 | 핵심 판타지 | 기본 무기 | 고유 자원 | 스킬 트리 3갈래 |
| --- | --- | --- | --- | --- |
| 인간 전사 (곤도르 변방의 경비병) | 균형형, 방패 패링 특화 | 장검 + 방패 | 투지(패링 성공 시 충전) | 수호자(방어) · 검사(콤보) · 지휘관(동료 게이지) |
| 엘프 궁수 (로험로리엔 정찰병) | 카이팅, 약점 저격 | 장궁 + 단검 | 집중(조준 유지 시 충전) | 명사수(저격) · 폭풍(다중 사격) · 빛의 가수(빛 마법) |
| 드워프 전사 (발린의 원정대원) | 탱커·버서커, 슈퍼아머 | 양손 도끼 | 분노(피격 시 충전) | 버서커(피해) · 철벽(생존) · 광부(폭약·광맥 식별) |

### 성장 시스템

- **레벨**: 필요 XP = `100 × level^1.5`. 레벨업 시 체력·공격력 자동 상승 + 스킬 포인트 1. 스탯 직접 분배는 넣지 않는다(스킬 트리가 그 역할을 한다).
- **장비**: 슬롯 6개(무기, 보조장비, 머리, 몸통, 장신구 2). 등급 5단계(일반 회색 → 정교 초록 → 희귀 파랑 → 엘프제/드워프제 보라 → 전설 금색). 전설은 고유 효과 1개를 갖는다.
- **강화**: 등불 대장간에서 미스릴 조각 + 금화로 +1\~+5. 실패 확률은 두지 않는다(확률 파괴 강화는 브라우저 게임 유저가 가장 빨리 이탈하는 요소).
- **인벤토리**: 그리드 40칸 + 자동 정렬 + "더 좋은 장비" 비교 화살표. 무게 제한은 두지 않는다.

### 캐릭터 외형과 이동 설계 (M0.5)

**M0의 플레이어는 방향도 얼굴도 없는 캡슐이었고 움직임도 로봇 같았다. 사실적 비율의 CC0 마네킹(Quaternius UAL)에 클래스별 복장을 입히고, 가속·회전 한도·발 위상 동기화가 있는 이동으로 바꿨다.** 문제는 여섯 가지였다: 알약 모양(방향이 안 읽힘), 몸이 항상 카메라를 봄(게걸음·뒷걸음), 즉시 최고속·즉시 정지, 애니메이션 없음, 카메라가 벡에서 튀고 모서리를 뚫어 봄, 횃불이 카메라 기준에 붙음.

| 후보 에셋 (둘 다 CC0) | 걸기 | 조깅·달리기 | 질주 | 비율 | 장점 | 단점 |
| --- | --- | --- | --- | --- | --- | --- |
| Quaternius UAL 마네킹 (채택) | 0.94 m/s | 5.6 m/s | 5.9 m/s | 사실적 | `Idle_Torch_Loop`·웅크리기·구르기, 게임 속도와 보폭이 맞음 | 얼굴 없는 마네킹, 전투 동작이 적음 |
| KayKit Adventurers 1.0 (비교용 `?rig=kaykit`) | 0.62 m/s | 2.65 m/s | — | SD(머리가 큼) | 완성된 의상·무기, 애니메이션 76개(방어·4방향 회피) | 다리가 짧아 조깅 4.2 m/s에서 다리가 파닥거리거나 미끄러짐, 톤 불일치 |

속도는 1.8m 환산, 접지 구간마다 (첫 접지 위치 − 마지막 위치) ÷ 접지 시간으로 잰 실측값이다. 처음 쓴 '발 앞뒤 폭 × 2' 방식은 달리기를 약 3분의 1로 과소평가했다(체공 구간 누락).

**이동 모델 (시뮬레이션, 결정적)**

| 클래스 | 키 | 걸기 / 조깅 / 질주 / 웅크림 (m/s) | 가속 / 감속 (m/s²) | 회전 (°/s, 질주 시) |
| --- | --- | --- | --- | --- |
| 인간 | 1.8m | 1.5 / 4.2 / 6.2 / 1.3 | 22 / 28 | 720 (400) |
| 드워프 | 1.4m, 가로 1.2배 | 1.3 / 3.8 / 5.6 / 1.2 | 26 / 32 | 720 (420) |
| 엘프 | 1.88m, 가로 0.92배 | 1.6 / 4.5 / 6.8 / 1.4 | 24 / 30 | 790 (440) |

- 몸은 카메라가 아니라 **이동 방향**으로 돈다. 회전 후에도 90° 넘게 어긋나면 속도를 20%로 줄여 발을 디디며 도는 U턴이 된다.
- 방향 계산에 필요한 atan2도 `Math.atan2`(명세상 구현 근사) 대신 급수로 만든 결정적 버전을 쓴다.
- 벽에 막히면 속도를 실제 이동량으로 맞춰, 벽에 대고 제자리 달리기하지 않는다.

**애니메이션 (렌더 전용)**: 속도에 따른 1D 블렌드(대기→걸기→조깅→질주), 재생 배속 = 실제 속도 ÷ 클립의 무미끄럼 속도(로드 때 실측), 모든 보행 클립을 하나의 위상으로 돌리고 왼발 접지 시점을 맞춤, 낙하·착지, 가속 시 앞으로·선회 시 안쪽으로 기울임. 횃불은 왼손에 들고, 그 팔은 `Idle_Torch_Loop`에서 떼어 낸 레이어로 고정한다.

**카메라**: 수평은 빠르게·수직은 느리게 따라가고(계단에서 덜컹임 없음), 반지름 0.22m 구체를 쏴 벽에 걸리면 즉시 당기고 천천히 돌아간다. 질주 시 시야각 62° → 70°.

**조작 변경**: 질주는 Space 길게 누르기(짧게 누르면 M1에서 회피), C는 웅크리기 토글, 게임패드 반 기울임은 걸기다. 이로써 조작표의 Space = 회피, Shift = 패링과 충돌하지 않는다.

**구현 중 찾은 버그**: 접지 중 캐릭터를 아래로 누르던 속도(−1 m/s)가 캡슐을 컨트롤러 offset 안으로 밀어 넣어 Rapier KCC가 간헐적으로 수평 이동을 막았다(370틱 중 9회 멈칫). M0에서는 즉시 최고속 모델이라 가려져 있다가 가속을 넣자 드러났다 → 0으로 고치고 회귀 테스트를 추가했다.

### NPC (레벨 2 상호작용)

- 등불마다 상주 NPC 3명: 상인(소모품·장비), 대장장이(강화), 동료 캐러클(로어·호출 강화).
- 대화는 분기 선택지 최대 3개, 퀘스트 수주/완료와 상점 열기로 이어진다. 호감도·도덕성 시스템은 1.0 범위에서 제외한다.
- 원정대원(간달프, 아라곤, 레골라스, 김리, 보로미르, 호빗 4인)은 등불에서 대화하고, 전투에서는 동료 호출로만 등장한다.

### 적 AI

적은 상태 머신(FSM) 하나로 돌린다: 대기 → 순찰 → 감지 → 접근 → 공격 → 후퇴·경직. 행동 트리 라이브러리는 보스에만 필요하면 도입한다. 길찾기는 구역마다 구운 내비메시를 `navcat`으로 질의한다.

## 11. 렌더링·그래픽·에셋 파이프라인

**`WebGPURenderer` 하나로 WebGPU와 WebGL2를 모두 커버하고, 셰이더·포스트프로세싱은 전부 TSL(Three Shading Language)로 작성한다.** TSL은 WGSL과 GLSL로 각각 컴파일되므로 폴백 경로에서도 같은 코드가 돈다. 기존 `EffectComposer`와 `ShaderMaterial`(GLSL 문자열)은 WebGPURenderer와 호환되지 않으므로 쓰지 않는다.

```ts
import * as THREE from 'three/webgpu';

const renderer = new THREE.WebGPURenderer({ antialias: true });
await renderer.init(); // 백엔드 결정(WebGPU 또는 WebGL2)은 여기서 끝난다
const isWebGPU = renderer.backend.isWebGPUBackend === true;
// KTX2Loader.detectSupport(renderer)는 반드시 init() 이후에 호출
```

r183부터 후처리 진입점은 `RenderPipeline`(구 `PostProcessing`)이다. 다수 광원은 r185의 `ClusteredLighting`(구 `TiledLighting`)으로 처리하고, `PCFSoftShadowMap`은 r186에서 제거됐다. M0 구현에서 확인한 사실: ClusteredLighting은 컴퓨트 셰이더로 클러스터를 계산하고 r186 공식 예제도 WebGPU가 없으면 중단하므로 WebGPU 전용이다. WebGL2 폴백에서는 기본 조명에 가까운 횃불 6개로 광원을 옮겨 단다. 그림자를 드리우는 점광원은 클러스터에서 빠지고 일반 경로로 처리된다(소스 확인). 같은 이유로 물결·파티클도 `forceWebGL: true`로 따로 검증하고, 폴백 시 CPU 경로를 둔다.

### 비주얼 방향

- **어둠이 기본값**: 앰비언트 조명은 거의 0, 보이는 것은 횃불·등불·미스릴 광맥·용암뿐이다. 정적 조명은 Blender에서 라이트맵으로 구워 런타임 라이트를 줄인다.
- **스케일감**: 21번째 홀의 기둥은 높이 30m 이상, 먼 부분은 높이 안개로 사라지게 한다. 모리아의 본질은 '어둠 속 거대함'이다.
- **색 대비**: 차가운 돌(청회색) vs 따뜻한 불(주황) vs 스팅·미스릴(청백). 세 색만으로 위험·안전·보상을 구분한다.

### 포스트프로세싱과 품질 티어

| 효과 | Low (모바일·내장 GPU) | Medium | High (PC 외장 GPU) |
| --- | --- | --- | --- |
| 렌더 해상도 | 0.66배 + 업스케일 | 0.85배 | 1.0배(devicePixelRatio 최대 2) |
| 동적 그림자 | 횃불 1개, 512px | 횃불 1개, 1024px | 횃불 + 보스 화염, 2048px |
| Bloom | 끄기 | 켜기(반해상도) | 켜기 |
| AO (GTAO) | 끄기(라이트맵 AO만) | 끄기 | 켜기 |
| 포그 | 지수 포그 | 높이 포그 | 높이 포그 + 먼지 파티클 |
| 파티클 상한 | 500 | 2,000 | 10,000 (WebGPU 컴퓨트) |
| 톤매핑·비네트 | 켜기 | 켜기 | 켜기 |

초기 티어는 부트 시 3초 벤치마크(평균 프레임 시간)로 자동 선택하고, 플레이 중 5초 이상 목표 FPS를 못 맞추면 한 단계 내리도록 제안한다(강제 변경은 하지 않음).

### 에셋 파이프라인

1. Blender에서 glTF 2.0(.glb)로 내보낸다. 콜리전은 `_col` 접미사를 붙인 별도 저폴리 메시로 함께 내보낸다.
2. `gltf-transform`으로 최적화한다: `dedup` → `weld` → `simplify`(LOD용) → `draco`(정적 지오메트리) 또는 `meshopt`(스킨·애니메이션 메시).
3. 텍스처는 KTX2로: 베이스컬러는 ETC1S(작게), 노멀·ORM은 UASTC(품질). 최대 2048px, 모바일은 1024px 변형을 별도 생성한다.
4. 애니메이션은 클래스별 공용 스켈레톤 하나에 모아 리타게팅 없이 공유한다.

- 모든 외부 에셋은 `CREDITS.md`에 출처와 라이선스를 기록한다.

## 12. 물리·오디오·저장

**물리는 '이동과 막힘'에만 쓰고, 전투 판정은 물리 엔진 밖의 간단한 히트박스 검사로 처리한다.** 칼날 충돌을 물리로 판정하면 프레임마다 통과·누락이 생기고 튜닝이 어렵다. 액션 게임의 타격감은 '애니메이션 프레임 구간 × 구/박스 겹침 검사'가 더 안정적이다.

### 물리·충돌 (Rapier)

| 대상 | 콜라이더 | 바디 타입 |
| --- | --- | --- |
| 플레이어·적 | 캡슐 | Kinematic (KinematicCharacterController로 경사·계단 처리) |
| 지형·벽 | 간략화 trimesh(`_col` 메시) | Fixed |
| 기둥·상자 | 박스·원기둥 | Fixed |
| 부서지는 물체(트롤이 부수는 기둥 등) | 박스 조각 5\~8개 | Dynamic, 5초 후 sleep·제거 |
| 화살·투사체 | 바디 없음 | 매 틱 레이캐스트(`castRay`) |
| 트리거(구역 진입·등불) | 박스 센서 | Fixed + sensor |

물리 스텝은 게임 루프의 고정 60Hz에 맞춘다. 충돌 그룹(플레이어/적/지형/투사체)을 처음부터 나눠 두면 "적끼리 끼어 움직이지 못함" 류의 버그가 줄어든다.

### 오디오

- **적응형 음악 3레이어**: 탐험(저음 드론) · 긴장(멀리서 들리는 북) · 전투(타악기 풀). 같은 BPM·같은 길이로 동시에 재생하고 볼륨만 크로스페이드한다. 어느 레이어를 올릴지와 북 BPM은 C 북소리 디렉터의 상태가 정한다(6장 표).
- **효과음**: 구역별 오디오 스프라이트 1개(WebM Opus + MP3 폴백). 타격음은 변형 3개를 무작위로 + 피치 ±5%로 반복감을 없앤다.
- **공간 음향**: `THREE.PositionalAudio`(HRTF)로 적의 방향을 귀로 찾게 한다. 어둠이 핵심인 게임에서 소리는 두 번째 시야다. 넓은 홀에만 ConvolverNode 리버브를 걸고 좁은 통로는 드라이하게 둔다.
- **음성**: 원정대의 짧은 호출음만 자체 대사로 녹음하고, 나머지 대화는 텍스트다. 원작·영화 대사는 인용하지 않는다.
- 브라우저 자동재생 정책때문에 첫 클릭("모리아로 들어가기")에서 `AudioContext`를 resume한다.

### 저장·로드

- 저장소: 세이브는 IndexedDB(`idb-keyval`), 리플레이는 OPFS + `CompressionStream`, 설정(그래픽·키 바인딩·볼륨)만 localStorage.
- 슬롯: 자동 저장 1개(등불 점등·구역 전환·보스 처치 시) + 수동 3개(등불에서만). 전투 중 저장은 허용하지 않는다. 2분마다 메모리에만 경량 체크포인트를 만들어 리플레이 시작점으로 쓴다.
- 스키마: `{ version, character, inventory, quests, zoneFlags, litBraziers, playTime, seed }`. 버전이 오르면 `migrate(v)` 함수가 순서대로 변환한다.
- 데이터 손실 방지: 새 세이브를 쓴 뒤 이전 것을 지우는 2단계 쓰기, 불러오기 실패 시 직전 세이브로 복구. JSON 내보내기·가져오기로 브라우저 데이터 삭제에 대비한다.
- `navigator.storage.persist()`를 요청해 브라우저가 저장소를 임의로 비우지 않게 한다.

## 13. UI/HUD·입력·접근성

**HUD는 HTML/CSS 오버레이로 만들고, 전투 중에는 화면 가장자리 4곳에만 둔다.** 어두운 게임일수록 HUD가 화면을 가리면 분위기가 깨진다. 비전투 5초 후 체력바·스킬바는 흐려지게(opacity 0.3) 한다.

| 위치 | 요소 | 비고 |
| --- | --- | --- |
| 좌하단 | 체력 · 스태미나 · 클래스 자원 · 동료 게이지 | 피해 시 뒤처진 흰 바가 천천히 줄어드는 '지연 체력바' |
| 하단 중앙 | 스킬 4칸 + 포션 | 쿨다운은 원형 스위프 |
| 우상단 | 미니맵(밝힌 곳만) + 퀘스트 추적기 1줄 | 미니맵은 탑뷰 직교 카메라를 저해상도로 렌더 |
| 상단 중앙 | 보스바(보스전에서만) | 페이즈 경계 눈금 표시 |
| 월드 내 | 적 체력바, 피해 숫자, 락온 표식 | 스프라이트(인스턴싱)로 그려 DOM 노드를 늘리지 않음 |

### 메뉴 화면

- 인벤토리·장비 / 스킬 트리 / 퀘스트 로그 / 지도 / 로어(마자르불의 책) / 설정 — Tab으로 열고 Q·E로 탭 전환.
- 메뉴를 열면 게임을 일시정지한다(싱글 게임이므로).
- UI 스타일: 드워프 룬 문양 테두리 + 양피지 질감. 폰트는 라틴은 Cinzel, 한글은 나눔명조(둘 다 OFL).

### 입력

- 키보드·마우스(Pointer Lock API)와 Gamepad API를 같은 액션 매핑 계층으로 추상화한다. 마지막으로 쓴 장치에 따라 버튼 아이콘이 바뀐다.
- 모바일(Low 티어): 가상 조이스틱(좌) + 공격·회피·스킬 버튼(우), 자동 락온 기본 켜짐.

### 접근성 (기본 탑재)

- 모든 키 리바인드, 홀드/토글 전환.
- 자막 크기 3단계 + 화자 이름 표시, 색각 이상 보정 모드(적 경고 색을 색+모양으로).
- 화면 흔들림·카메라 모션 블러 끄기, 밝기 보정(어둠이 핵심이라 필수).
- 난이도 3단계 + '스토리' 모드(피해 50%, 패링 창 2배).

## 14. 성능 예산·최적화·메모리

**예산은 숫자로 고정하고, 매 마일스톤마다 재는다.** 예산을 넘는 기능은 품질 티어 뒤로 숨기거나 자른다. 디버그 빌드는 `renderer.info`의 draw call·삼각형·지오메트리·텍스처 수를 화면에 상시 표시한다.

| 항목 | PC High | 모바일 Low |
| --- | --- | --- |
| 프레임 | 60 FPS (16.6ms) | 30 FPS (33.3ms) |
| Draw call | ≤ 300 | ≤ 100 |
| 화면 내 삼각형 | ≤ 1.5M | ≤ 300K |
| 동적 광원 (ClusteredLighting) | ≤ 64 | ≤ 16 |
| 그림자 드리우는 광원 | 2 | 1 |
| 실제 AI 적 (T0 + T1) | 48 | 20 |
| 물결 전체 (T0\~T2) | 200 | 60 |
| 텍스처 메모리(GPU) | ≤ 512MB | ≤ 150MB |
| 시뮬레이션 틱 (물리 + AI + 디렉터) | ≤ 4ms | ≤ 8ms |
| 초기 다운로드(첫 구역까지) | ≤ 25MB | ≤ 15MB |

### Draw call 줄이기

- **인스턴싱**: 기둥·돌·횃불 같은 반복 소품은 `InstancedMesh` 하나로. 모듈러 키트 방식과 궁합이 가장 좋다.
- **정적 병합**: 움직이지 않는 환경은 머티리얼별로 `mergeGeometries` 또는 `BatchedMesh`로 묶는다.
- **텍스처 아틀라스**: 환경 키트는 머티리얼 3\~4개(돌·금속·나무·발광)를 공유하게 제작한다.
- **컴링**: 구역을 방(room) 단위로 나누고, 방끼리 연결된 문(포털) 기반으로 보이는 방만 그린다. 동굴 던전은 시야가 벽에 막히므로 효과가 크다.
- **LOD**: 캐릭터·큰 소품은 2단계, 먼 적은 애니메이션 갱신 주기를 1/2로.

### 로딩 전략

1. 부트: 코어 코드 + 공용 에셋(플레이어, UI, 공용 효과음)만. `LoadingManager`로 진행률 표시, 로딩 화면에는 로어 팁 문구.
2. 구역 진입: 해당 구역 모듈을 동적 import + 에셋 로드. 구역 사이에는 '긴 계단·좁은 통로' 같은 연결 구간을 두어 로딩을 가린다.
3. 미리 가져오기: 구역 진행도 70%가 되면 다음 구역 에셋을 백그라운드에서 받는다.
4. 콜드 스타트: 셰이더 컴파일 끊김을 막기 위해 로딩 화면에서 `renderer.compileAsync(scene, camera)`를 미리 호출한다.

### 메모리 관리

- 에셋 매니저가 URL별 참조 카운트를 들고 있다. 구역을 떠날 때 카운트가 0인 것만 geometry·material·texture를 `dispose()`한다. 공용 에셋(플레이어 등)은 카운트가 남아 자연스럽게 유지된다.
- `Material.dispose()`는 연결된 텍스처를 지우지 않는다. 텍스처는 별도로 추적해 지운다.
- Rapier 바디·콜라이더도 구역 해제 시 `world.removeRigidBody()`로 명시적으로 제거한다(WASM 힙은 GC 대상이 아니다).
- 검증: 구역 1→2→1을 10회 왕복한 뒤 `renderer.info.memory`의 geometries·textures 수가 처음과 같아야 한다(자동화 테스트로 둠).

## 16. 실제 구현 요청 프롬프트

**프롬프트는 "마스터 컨텍스트 1개 + 마일스톤별 작업 프롬프트 6개"로 나눈다.** 게임 전체를 한 번에 만들어 달라는 프롬프트는 거의 항상 돌아가지 않는 데모로 끝난다. 마스터 컨텍스트는 저장소 루트의 `CLAUDE.md`(또는 `AGENTS.md`)에 두고, 각 단계는 새 세션에서 작업 프롬프트 하나씩 넘긴다.

### 마스터 컨텍스트 (CLAUDE.md)

```markdown
# 모리아의 그림자 — 프로젝트 규칙

## 제품
반지의 제왕 모리아 광산 배경 3인칭 실시간 핵앤슬래시 던전 크롤러(비상업 팬 프로젝트).
구역 5개, 클래스 3종(인간 전사/엘프 궁수/드워프 전사), 최종 보스 발로그.
핵심 루프: 탐험 → 전투 → 보상 → 강화(등불) → 다음 구역, 1사이클 약 15분.

## 재미의 기둥 (계획서 4~6장)
- 감지 필드: gameplay/perception.ts의 lightAt()/noiseAt() 하나로 모든 적 인지와 '빛의 도박' 보상을 계산
- 긴장도 디렉터: Relax → BuildUp → Peak → Fade. 상태 = 북소리 BPM. 스폰 규칙 3개(시야 밖, 어둠, 15m 이상)
- 결정적 코어: 같은 시작 상태 + 같은 입력 → 같은 결과. 리플레이·핏자국·시드 던전의 기반

## 스택 (바꾸지 말 것)
- Vite + TypeScript strict, 단일 패키지 (+ worker/ 는 선택)
- three@0.186.x 고정, 'three/webgpu' import, WebGPURenderer(WebGL2 자동 폴백)
  - 셰이더·후처리는 TSL + RenderPipeline만. EffectComposer, ShaderMaterial, onBeforeCompile 금지
  - 다수 광원은 ClusteredLighting(WebGPU 전용), WebGL2 폴백은 가까운 횃불 N개 광원 풀. PCFSoftShadowMap 사용 금지(r186 제거)
- 물리: @dimforge/rapier3d-compat@0.21, 캐릭터는 KinematicCharacterController
- 길찾기·군중: navcat (버전 고정)
- UI: preact + @preact/signals, HTML/CSS 오버레이
- 오디오: howler(BGM·UI), THREE.PositionalAudio(HRTF)
- 저장: idb-keyval(세이브), OPFS + CompressionStream(리플레이), 설정만 localStorage
- 온라인(선택): Cloudflare Workers + Durable Objects. 오프라인에서도 게임은 완결돼야 함
- 에셋: glTF(.glb) + Draco/Meshopt + KTX2

## 결정성 규칙 (위반 시 리뷰 거절)
1. 게임 로직은 고정 60Hz 틱에서만, dt는 항상 1/60
2. Math.random 금지 → core/rng.ts 시드 난수
3. 시뮬레이션에서 Math.sin/cos/atan2 금지 → core/trig.ts 표
4. 엔티티 순회·Rapier 바디 생성은 ID 순서. 비동기 로딩 완료 순서에 의존 금지
5. 히트박스는 AnimationMixer 시간이 아니라 시뮬레이션 틱 기준
tests/determinism.test.ts 는 항상 통과해야 한다.

## 아키텍처 규칙
- ECS-lite: 엔티티 = 컴포넌트를 가진 평범한 객체, 시스템 = (world) => void
- UI·오디오는 이벤트 버스를 구독만 한다. 게임 로직이 DOM을 직접 만지지 않는다
- 밸런스 수치·아이템·적·퀘스트·디렉터·룬 문구는 data/*.json. 코드에 매직 넘버 금지
- 구역은 src/zones/*.ts 동적 import. 퇴장 시 참조 카운트 기반 dispose + Rapier 바디 제거
- 새 의존성 추가 전에 이유를 설명하고 확인받을 것

## 성능 예산
PC High 60FPS, draw call ≤ 300, 광원 ≤ 64, 물결 200 / 모바일 Low 30FPS, draw call ≤ 100, 광원 ≤ 16, 물결 60
```

## 17. 리스크·IP·테스트 전략

**가장 큰 리스크는 기술이 아니라 IP다. 비상업 팬 프로젝트로 공개하고, 상업화 가능성이 있다면 처음부터 오리지널 세계관으로 바꿀 수 있게 만든다.** '반지의 제왕' 고유명사와 상표의 게임 라이선스는 별도 권리자가 관리하므로, 수익화(광고·후원 포함)는 법적 검토 없이 하지 않는다. 고유명사를 모두 `data/lore.json`에 모아 두면 이름 교체가 파일 하나 수정으로 끝난다.

| 리스크 | 가능성 | 영향 | 대응 |
| --- | --- | --- | --- |
| IP 이의 제기(테이크다운) | 중 | 고 | 비상업, 영화 자산 미사용, 고유명사 데이터 분리, "비공식 팬 게임" 고지 |
| Nemesis 특허(US10926179B2, 2036 만료 예상) 저촉 | 중 | 고 | 개별 적이 사건 후 변해서 돌아오는 설계 금지. 디렉터는 개체가 아니라 스폰 규모·시점만 조절. 공개 전 법률 검토 |

### 테스트 전략

- **단위(Vitest)**: 피해 계산, XP 곡선, 퀘스트 상태 전이, 세이브 마이그레이션, 공격 토큰 배분. 렌더링이 없는 순수 로직만.
- **스모크(Playwright)**: 부트 → 새 게임 → 이동 → 저장 → 새로고침 → 이어하기, 콘솔 에러 0. 게임에 `window.__game` 테스트 훅(개발 빌드만)을 두어 상태를 읽는다.
- **성능 회귀**: 고정 카메라 경로 벤치마크 장면 1개를 만들고, 평균 프레임 시간·draw call을 마일스톤마다 기록한다.
- **플레이테스트**: G1·G2에서 외부 5명. 질문은 3개만 — 어디서 막혔나, 가장 좋았던 순간, 다음 구역을 하고 싶은가.

| 프로덕션 번들 | 5.2MB (gzip 1.9MB), 이 중 Rapier WASM 4.1MB. 개발 도구 미포함 확인 |

구현 중 발견해 고친 것:

- **계획 오류**: ClusteredLighting을 WebGL2에서도 쓸 수 있다고 적었으나 WebGPU 전용이었다 → 3·6·11·16장 수정.
- **삼각함수 표**: 테일러 급수를 π/2까지 쓰면 sin(90°)=1.0000000000000002가 된다 → 45° 이후는 cos 급수로 계산.
- **레벨 데이터**: 경사로 윗끝이 윗단보다 0.11m 솟은 턱 → 높이 보정 후 결정성 기준값 재생성.
- **개발 환경**: WSL의 `/mnt/c`에서는 파일 변경 알림이 없어 Vite가 수정 전 코드를 내주었다 → `server.watch.usePolling`.
- **확인해서 맞았던 것**: three r186의 `RenderPipeline`·`PCFSoftShadowMap` 제거·`ClusteredLighting` 존재, Rapier 0.21 API와 결정성 보장, `Math.sqrt`는 명세상 정확 / `Math.sin`은 구현 근사(ECMA-262).

남은 한계: 이 환경에는 GPU가 없어 프레임률(소프트웨어 렌더링 4\~10 FPS)은 측정하지 못했다. 실제 GPU가 있는 PC에서 확인이 필요하다. CI도 아직 구성하지 않았다.

- **던진 횃불 = 구 → 막대**: Rapier에는 구름 저항이 없어 구가 끝없이 굴렀다(테스트).
- **타격 순간 맞춤**: 공격 클립의 손 속도 최대 시점을 로드 때 재고, 시뮬레이션 판정 틱에 맞춰 시간을 왜곡한다.
- **드로우콜**: 손 횃불이 제 그림자를 드리워 빛을 가리고 있었다 → 소품·계단 한 칸 그림자 끄기(189 → 163).
- **보조광**: 카메라가 벽에 걸려 다가오면 투구가 하얗게 탔다 → 거리²에 비례해 줄임.
- **계획과 다른 점**: 전투 수치는 data/combat.json이 아니라 타입이 있는 `src/sim/combat.ts` 상수다. JSON 이관은 M3 데이터 작업과 함께.
- **내비메시 생성 1초**: 시작 시간에 더해진다 → M2에서 구역별로 미리 굽는다.

**아트 방향 결정 → 리타게팅 (사용자 선택)**: 사실 비율 UAL 마네킹을 유지하고, KayKit의 전투 동작 7종(내려찍기·대각·수평·찌르기·양손 내려찍기·앞 회피·막기)을 UAL 뼈대로 옮겼다 (`src/render/retarget.ts`). 피격·사망은 UAL 자체 동작을 쓴다.

- **three.js `SkeletonUtils.retarget`을 쓰지 않은 이유**: 소스를 읽어 보니 원본 뼈의 월드 회전을 그대로 넣는다 → 두 리그의 뼈 축 규약과 기본 자세가 같아야만 맞는다. UAL(Rigify, A-포즈)과 KayKit(자체 리그, T-포즈)은 둘 다 다르다.
- **방식**: 각 리그의 대기 자세를 기준으로 월드 회전 변화량 D = Q\_src(t)·Q\_src(ref)⁻¹을 재고, 대상에 Q\_tgt(t) = D·Q\_tgt(ref)로 적용한다. 엉덩이 이동은 엉덩이 높이 비율로 줄인다.
- **검 쫘는 방향**: 임의 각도로 쫘면 찌르기가 찌르기로 안 보였다 → KayKit 대기 자세의 검 방향을 그대로 쓰되, 평상시에는 늘어뜨린 방향과 행동 가중치로 섞는다.
- **패링**: KayKit Block은 방패(왼팔) 동작이라 좌우 반전(변화량 (x,y,z,w)→(x,−y,−z,w))해 검 막기(오른팔)로 썼다.
- **검증**: 타격 순간 실측이 원본과 거의 같다(내려찍기 0.58→0.62s, 대각 0.38, 수평 0.25, 찌르기 0.39). 로드 시간 추가는 체감 불가(부팅 약 1.5초). 비교 시트는 `docs/review/m1-retarget-*.png`.
- **남은 것**: KayKit Knight.glb(3.6MB)를 동작 추출용으로 내려받는다 → 리타게팅 결과를 빌드 단계에서 구워 파일로 두면 없앨 수 있다. 손가락은 검을 쥐지 않은 편 자세 그대로다.

### M2-A — 긴장도 디렉터·북소리·빛의 내기·돌의 감각

**디렉터가 긴장도에 따라 고블린 무리를 보내고, 북소리가 그 단계를 소리로 알린다. 어두운 곳의 일격은 강해지고, V 한 번으로 주변 지형과 움직이는 적이 드러난다.** 테스트 49개가 통과하고, 새 골든 해시(10초)와 긴 해시(100초, 디렉터 포함)가 Node와 Firefox 155에서 일치한다. WebGPU와 WebGL2 화면이 같다.

- **디렉터 단계**: 휴식 30\~45초 → 고조 40\~70초(긴장도 0.7 이상이면 즉시 경고) → 경고 8초 → 절정 → 소강(최대 60초). 스폰 조건은 세 가지다. 시야 밖, 밝기 0.2 미만, 경로 거리 15m 이상.
- **계획과 달라진 점 1 — 스폰 판정은 무리 중심이 아니라 고블린마다 한다.** 중심만 숨으면 무리 일부가 플레이어 눈앞에 나타났다.
- **계획과 달라진 점 2 — 절정 종료.** 긴장도만 보면 무리가 도착하기도 전에 절정이 끝났다. 지금은 세 조건 중 하나로 끝난다. 무리 전멸, 절정 중 긴장도가 0.5를 넘은 뒤 0.3 미만으로 떨어짐, 30초 경과.
- **계획과 달라진 점 3 — 소강에 60초 상한.** 상한이 없으면 고블린 한 마리가 숨어 있는 동안 소강이 끝나지 않았다.
- **빛의 내기**: 플레이어 가슴 높이의 밝기로 피해 배율을 정한다. 배율 = 1 + 0.5 × (1 − 밝기). 완전한 어둠이면 1.5배이고 "어둠의 일격" 알림이 뜬다.
- **돌의 감각**: 재사용 8초. 쓰면 15m 소음을 3초 동안 내므로 대가가 있다. 반경은 종족별이고 드워프는 30m다. 반경 안의 움직이는 고블린은 발광하고, 후처리 음파가 지나간 자리의 모서리가 드러난다.
- **북소리**: Web Audio로 합성하며 음원 파일이 없다. 디렉터 BPM에 맞춰 앞질러 예약한다. 단계가 절정에 가까울수록 소리가 크고 필터가 열린다.
- **구현 중 발견 1 — 후처리 카메라 행렬.** TSL 후처리 출력 노드에서 `cameraProjectionMatrixInverse`·`cameraWorldMatrix`는 장면 카메라가 아니라 화면 사각형을 그리는 카메라를 가리킨다. 그래서 음파가 보이지 않았다. three의 GTAONode처럼 `uniform(camera.projectionMatrixInverse)`·`uniform(camera.matrixWorld)`를 직접 넘겨 고쳤다.
- **구현 중 발견 2 — 윤곽 판정.** 깊이 기울기 `fwidth(z)`의 절대값은 비스듬한 바닥에서도 커져 화면 전체가 하얗게 떴다. 깊이로 나눈 상대값에 임계(0.04\~0.12)를 걸자 실제 모서리만 남았다.
- **검증 자료**: `docs/review/m2a-sense-webgpu.png`, `docs/review/m2a-sense-webgl2.png`.
- **남은 일(M2 나머지)**: 두린의 문 수수께끼, 1구역 방·포털 컬링, 드워프 화로 체크포인트와 저장(idb-keyval), 동굴 트롤 중간 보스, 품질 단계, 내비메시 사전 굽기. 번들은 5.5MB 한 파일이라 M5 이전에 코드 분할이 필요하다.

### M2-B — 구역 1·두린의 문·화로·저장

**서문 밖에서 시작해 두린의 문을 열고, 입구 홀과 거대 계단을 지나 기둥 홀과 트롤 굴까지 걸어갈 수 있다.** 화로에서 쉬면 저장되고, 새로고침하면 그 화로에서 이어한다. 테스트는 60개로 늘었다. 구역 1 골든 해시(50초, 문 열기 포함)는 Node와 Firefox 155에서 일치한다.

- **구역 데이터**: `zone1.ts`의 방은 5개다. 서문 밖, 입구 홀, 거대 계단(20단, 4m 오름), 기둥 홀(척후 고블린 5), 트롤 굴이다. 통로는 4개이고 화로는 3개다. 방의 벽·바닥·천장은 모두 방 경계 안에 만든다. 그래서 방 하나를 숨겨도 이웃 방에 구멍이 생기지 않는다.
- **문과 화로는 입력 비트로 처리한다.** E(화로)와 암호 정답(`BTN_WORD`)은 시뮬레이션 입력 프레임에 실린다. 그래서 리플레이가 문 열기까지 재현한다. 문이 닫힌 동안에는 디렉터가 쉬고, 닫힌 문 너머의 방은 그리지 않는다.
- **계획과 달라진 점 1 — 수수께끼 허용 거리.** '모두 편집 거리 ≤ 2'를 테스트해 보니 두 가지 구멍이 있었다. 두 글자 답('친구')은 아무 두 글자나 통과했고, 'hello'는 mellon과 거리가 2라서 통과했다. 그래서 허용 거리를 ⌊길이/4⌋로 바꿨다. 비문이 '벗이여'라고 부르므로 '벗'도 정답에 넣었다.
- **계획과 달라진 점 2 — 저장은 localStorage로 한다.** 저장 데이터는 1KB 미만의 JSON 하나다. `setItem`은 값을 통째로 바꾸므로 '반쯤 쓴 저장'이 생기지 않는다. 그래서 idb-keyval과 2단계 쓰기는 필요 없었다. 버전 검사와 모양 검사는 하고, 틀리면 새 게임으로 시작한다.
- **계획과 달라진 점 3 — 구역 재진입 메모리 기준은 M3로 옮긴다.** M2에는 구역이 하나뿐이고, 쓰러지면 페이지를 새로고침해 저장에서 이어한다. 같은 페이지에서 구역을 내렸다 올리는 일은 구역이 둘 이상인 M3에서 생긴다.
- **포털 컬링**: 방마다 도형을 (재질, 그림자)별로 합친다. 통로 상자가 시야에 걸리는 방만 그리고, 안 보이는 방의 고블린은 그리기와 애니메이션을 모두 건너뛴다. 서문 밖에서 draw call이 149에서 41로 줄었다. 고블린이 보이는 기둥 홀은 여전히 약 140이고, 대부분은 횜불 점광원 그림자(6면)다. 품질 단계에서 다룬다.
- **구현 중 발견**: 비문 창을 여는 E가 방금 포커스를 받은 입력창에 'e'로 들어갔다(“ehello”). keydown에서 기본 동작을 막아 고쳤다. 게임 조작은 글자 입력창에 칠 때 받지 않는다.
- **음성**: `SpeechRecognition.available({langs:['en-US'], processLocally:true})`가 `'available'`일 때만 마이크 버튼을 보인다. 언어팩 설치(`install`)와 클라우드 인식은 하지 않는다. 게임패드만으로는 비문에 답할 수 없어 키보드가 필요하다.
- **검증 자료**: `docs/review/m2b-zone1-webgpu.png`, `docs/review/m2b-zone1-webgl2.png`.
- **남은 일(M2-C)**: 동굴 트롤 중간 보스(내리찍기 예고 1초, 휘두르기, 기둥 파괴), 품질 단계(Low는 그림자 끄기), 내비메시 사전 굽기.

### M2-C — 동굴 트롤·품질 단계·내비메시 사전 굽기 판단

**트롤 굴의 동굴 트롤은 규칙 세 가지로 싸운다.** 내려찍기는 1초 예고 뒤 원형 범위를 치고 패링할 수 없다. 휘두르기는 기둥에 막히고 패링할 수 있다. 트롤은 빛에 끌린다. 테스트는 68개이고, 트롤전 골든 해시(30초)를 포함한 네 가지 골든이 Node와 Firefox 155에서 일치한다.

- **내려찍기(예고 60틱, 피해 40, 패링 불가)**: 예비 동작 앞 2/3 동안은 겳냥점이 목표를 따라오고, 그 뒤에는 고정된다. 바닥의 붉은 고리가 1초 동안 차오른다. 겳냥점 가까이에 기둥이 있으면 기둥이 부서지고 트롤이 150틱 동안 휘청인다. 기둥은 숨을 곳이자 한정된 자원이다.
- **휘두르기(예고 38틱, 부채꼴 150°, 사거리 4m)**: 트롤과 플레이어 사이의 허리 높이 시선이 기둥에 막히면 빗나간다. 패링하면 트롤이 70틱 휘청이고 반격 배수가 붙는다.
- **빛 유인**: 플레이어가 5m보다 멀고 트롤 쪽에 더 가까운 횜불이 10m 안에 있으면, 트롤은 그 횜불로 가서 내려찍어 끈다. 횜불 던지기가 유인 수단이 된다.
- **보스전 규칙**: 집에서 24m 넘게 끌려 나가면 돌아가 체력을 되찾는다. 깨어 있는 동안에는 디렉터가 물결을 부르지 않는다. 처치하면 바로 저장하며, 저장은 v2로 올렸다(`bossesDown` 추가, v1 저장은 이전된다).
- **외형**: 같은 UAL 마네킹을 키 3.3m로 키운다. 배는 1.25배, 가슴은 1.1배(부모 뼈 크기를 이어받아 가슴 전체는 1.375배), 머리는 0.6배다. 클립에 뼈 크기 트랙이 있어 `mixer.update` 뒤에 다시 준다. 기술 애니메이션은 플레이어용으로 리타게팅한 클립을 빌린다. 강공격은 내려찍기, 수평 베기는 휘두르기에 쓰고 추가 다운로드는 없다. 잠든 트롤은 UAL의 앉아 있기 동작을 쓴다.
- **품질 단계**: Low는 그림자 없이 픽셀 비율 1, Medium은 그림자 512²에 픽셀 비율 1.5, High는 그림자 1024²에 픽셀 비율 2다. 기둥 홀의 draw call은 Low 53, Medium·High 159다. 개수는 Medium과 High가 같고 그림자 해상도만 다르다. 자동 감지는 터치 기기면 Low, 코어 4개 이하이거나 WebGL2면 Medium이다. 처음 5초 평균이 40 FPS 미만이면 한 단계씩 낮춘다.
- **계획과 달라진 점 — 내비메시 사전 굽기는 미룬다.** 구역 1은 Node에서 0.52초에 굽히고, JSON으로 저장하면 435KB다. 0.5초를 아끼려고 빌드 단계와 오래된 파일을 감시하는 일을 더하는 것은 지금은 손해다. 대신 캐릭터 파일 다운로드를 먼저 시작해, 내비메시를 굽는 동안 네트워크 대기가 같이 진행되게 했다. 구역이 커지는 M3에서 다시 잰다.
- **구현 중 발견**: 시험용 트롤전 골든의 처음 시작점은 트롤과 15m 떨어져 있었다. 30초 동안 트롤이 한 번도 깨지 않아 골든이 실제로는 트롤전을 포함하지 않았다. 사건 기록을 확인해 발견했고, 시작점을 7m 앞으로 옮겨 내려찍기 3회와 휘두르기가 들어가게 했다. 테스트는 트롤이 실제로 깨어났는지도 확인한다.
- **M2 완료 기준 현황**: 디렉터 시야 밖 스폰(Vitest), 새로고침 후 이어하기, 빛의 도박·북소리·돌의 감각은 충족했다. '새 게임에서 트롤 처치까지 약 15분'과 G1(외부 테스터 5명)은 사람이 플레이해야 칠 수 있다. 로드맵의 M2는 그때까지 체크하지 않는다.
- **검증 자료**: `docs/review/m2c-troll-webgpu.png`, `docs/review/m2c-troll-webgl2.png`.

### M3-A — 고블린 물결(B)

**북소리 절정에서 무리가 흐름장을 타고 밀려와, 횜불빛 경계 밖 어둠에서 한 마리씩 진짜 고블린이 된다.** 무리 176 + 진짜 24마리에서 시뮬레이션 틱은 0.48ms다(예산 4ms). 다섯 번째 골든(물결 20초)을 포함해 모든 골든이 Node와 Firefox 155에서 일치한다. 테스트는 77개다.

- **G1 게이트와 순서**: 계획상 M3 콘텐츠(구역 2\~4, 퀘스트, 성장)는 G1(사람의 플레이 평가) 뒤에 만든다. 그래서 G1 결과와 상관없이 필요하고 기술 위험이 가장 큰 물결(B)을 먼저 만들었다.
- **계획과 달라진 점 1 — T0와 T1을 합쳤다.** 공격권(동시 공격 2마리)이 이미 때리는 수를 제한한다. 진짜 고블린은 FSM·Rapier KCC·navcat 경로를 갖고 최대 24마리다. 나머지는 물리 없는 점이다.
- **계획과 달라진 점 2 — 흐름장은 CPU로 계산한다.** 1m 격자에서 정수 비용 다익스트라를 돌리며, 직선 10·대각 14의 버킷 큐를 쓰고 2Hz로 갱신한다. TSL 컴퓨트 없이 예산 안에 들어오고, 결정성도 지키기 쉽다. 내비메시는 격자의 바닥 높이를 정할 때 한 번만 쓴다.
- **빛의 경계**: 무리는 밝기가 0.5 이상인 곳에 들어가지 않는다. 든 횜불에서는 약 5.7m다. 승격은 밝기 0.2 미만(약 7.2m 밖)이면서 12m 안이고, 가까운 순서로 한다. 강등은 28m 밖의 어둠에서, 싸우는 중이 아닐 때만 한다. 바뀌는 순간이 보이지 않는다.
- **스키닝 인스턴싱 = VAT**: 고블린의 대기(12프레임)·달리기(24프레임) 자세를 CPU로 스키닝해 정점 위치를 텍스처에 굽는다(정점 8,547개, 5.6MB). 인스턴스마다 프레임 번호를 넘기므로 무리 전체는 draw call 하나다.
- **구현 중 발견 1 — positionNode의 적용 순서.** r186 `NodeMaterial.setupPosition`은 인스턴스 변환 뒤에 `positionNode`로 위치를 덮어쓴다. 그래서 위치·회전을 인스턴스 속성으로 따로 넘겨 셀이더에서 직접 적용한다. `instanceMatrix`는 법선 회전에만 쓴다.
- **구현 중 발견 2 — 흐름장 바닥이 지붕으로 잡혔다.** 내비메시에는 천장 지붕 윗면도 걸을 수 있는 면으로 들어 있다. 높이 한가운데서 가장 가까운 면을 찾자 기둥 홀(바닥 4m)에서 지붕(15m)이 잡혔다. 무리는 공중에 떠서 어둥다고 판정돼 승격됐다. 브라우저 통제 실험에서 발견했고, 레벨 맨 아래에서 찾도록 고쳤다. 천장이 없는 평면 테스트로는 잡히지 않아 구역 1 격자 높이 회귀 테스트를 더했다.
- **렌더 LOD**: 가까운 8마리만 스키닝으로 그리고, 나머지 진짜 고블린은 무리와 같은 VAT 메시로 그린다. 진짜 25 + 무리 42에서 Low draw call이 194에서 74로 줄었다.
- **남은 것**: PC에서 물결 200 + 60FPS는 실제 GPU가 있어야 잔다. 헤드리스 SwiftShader는 삼각형 280만 개를 CPU로 그려 초당 1프레임 수준이다. 무리는 이미 어둠 속 실루엣이라 멀리 있는 개체부터 저폴리 메시를 두는 것이 다음 후보다. 법선은 기본 자세 값이고 귀·칼 소품은 없다. 무너지는 모리아(E)와 동료 광역기는 M3-B에서 하고, 구역 2\~4·퀘스트·성장은 G1 뒤에 한다.
- **검증 자료**: `docs/review/m3a-horde.png`(WebGPU 줄 · WebGL2 줄 · LOD).

### M3-B — 무너지는 모리아(E)·동료 호출

**기둥 홀 양옆 고블린 굴 입구의 금 간 기둥을 부수면 쓰러지며 물결을 깔아뭉개고 굴을 막는다. 적을 쓰러뜨려 채운 게이지로 Q를 누르면 종족의 동료(아라곤·김리·레골라스)가 광역기를 쓴다.** 테스트는 87개이고, 골든 5종을 다시 만들어 Node와 Firefox 155에서 모두 일치한다.

- **계획과 달라진 점 — 내비메시 봉쇄**: 내비메시를 다시 굽지 않는다. 내비메시가 타일 하나라 재빌드하면 0.5초 멈춤다. 대신 `QueryFilter.passFilter`로 레벨이 지정한 봉쇄 영역(굴 안쪽)의 폴리곤을 뺀다.
- **계획과 달라진 점 — 봉쇄 범위**: 잔해 둘레 상자로 폴리곤을 빼면 기둥 홀의 큰 폴리곤까지 빠질 수 있다. 그래서 레벨 데이터에 봉쇄 영역(`seals`)을 명시한다.
- **'붕괴해도 출구 경로가 남는가'**: tools/ 스크립트 대신 Vitest로 검사한다. 두 기둥을 모두 무너뜨린 뒤에도 서문에서 트롤 굴까지 경로가 이어지는지 확인한다.
- **동료 호출 개선**: 브라우저에서 맞는 중에 누른 Q가 무시됐다. 쓰러졌을 때만 막고, 휘청임·히트스톱 중에도 받도록 바꿨다.
- **상세 기록**: 저장소 `docs/implementation-log.md`의 M3-B 항목에 있다. 이후 구현 기록은 그 문서에 더한다.

### M4-A — 마자르불의 책(F, 로컬)

**쓰러지면 발린 원정대 기록 문체로 한 줄이 책에 남고, B로 마지막 60초를 다시 볼 수 있다.** 원래 실행과 재생의 끝 상태 해시가 같은 것을 브라우저에서 확인했다. Firefox에서 스냅샷을 복원해 이어 돌린 해시도 Node 골든과 같다. 테스트는 95개다.

- **연결 방식**: 스냅샷은 Rapier 월드 스냅샷과 JS 상태 JSON으로 만든다. −0과 NaN은 표시를 붙여 보존한다. 2분 체크포인트는 한 번에 1.7ms다. 입력은 틱당 6바이트 XOR 델타를 deflate-raw로 압축해 OPFS에 둔다. 60초 파일은 20.9KB다.
- **빌드 호환**: 머리말에 빌드 때 계산한 `src/sim`·`src/core` 내용 해시를 넣는다. 값이 다르면 영상 대신 요약을 보여 준다. 렌더·UI만 바뀐 빌드에서는 옛 기록이 그대로 재생된다.
- **계획과 달라진 점**: 재생은 `?replay` 모드로 페이지를 다시 연다. 입력 공급원만 바꾸면 되어 코드가 가장 적다. 책 템플릿은 16종이다. 공유 링크는 M5의 서버 작업과 함께 한다.
- **상세 기록**: 저장소 `docs/implementation-log.md`의 M4-A 항목에 있다.

### M5-A — 출시 준비(기술 항목)

**셰이더 예열과 로딩 화면, 설정·접근성, 실제 브라우저 스모크 테스트(`npm run smoke`)를 넣었다.** 스모크는 20/20 통과다. 개발 서버에서는 새 게임 → 문 → 화로 저장 → 새로고침 → 이어하기를, 배포 빌드에서는 부팅과 이동을 확인한다. 둘 다 WebGPU·WebGL2에서 콘솔 에러가 0이다.

- **설정**: 화면 흔들림, 음파 세기, 밝기, 글자 크기, 마우스 감도·상하 반전, 색각 보정(빨강·주황 → 노랑·하늘색), 키 배치 바꾸기를 넣었다. 시뮬레이션 규칙은 바꾸지 않는다.
- **계획과 달라진 점**: Playwright 대신 이미 설치된 브라우저를 쓰는 puppeteer-core를 썼다. 서버(룬 메시지·리플레이 공유)와 배포는 계정이 필요하고 외부에 공개되는 작업이라 하지 않았다.
- **발견**: Vite의 build와 createServer는 같은 프로세스의 NODE\_ENV를 서로 바꾼다. 그래서 스모크에서 개발 훅이 사라지거나 배포 빌드에 개발 도구가 들어갔다. 빌드는 별도 프로세스로 격리했다.
- **상세 기록**: 저장소 `docs/implementation-log.md`의 M5-A 항목에 있다.

### M5-B — 모바일 터치 조작

**터치 기기에서는 화면 왼쪽이 가상 조이스틱, 오른쪽이 카메라다. 버튼 9개는 PC와 같은 탭/홀드 규칙을 따르고, 적이 8m 안에 오면 자동 락온된다.** 모바일 에뮤레이션(844×390)에서 이동, 공격, 자동 락온을 확인했고 스모크 테스트에도 넣었다.

- **발견**: 브라우저 자동화의 터치 에뮬레이션은 포인터 이벤트 좌표를 0으로 보낸다. 그래서 모든 모바일 브라우저가 지원하는 터치 이벤트로 구현했다.
- **남은 것**: 실기기(iOS Safari·Android Chrome) 확인이 필요하다. 상세는 `docs/implementation-log.md` M5-B.

### M3-C1 — 성장과 구역 2(21번째 홀)

**트롤을 쓰러뜨리면 21번째 홀로 넘어간다. 기둥 16개 사이 등불 셋을 밝히면 북문이 열린다. 레벨(최대 20)과 종족별 스킬 트리(3갈래 × 5단계)로 성장한다.** 테스트는 109개다.

- **계획과 달라진 점**: 스킬은 단계당 1노드(15노드)다. 활이 없어 엘프 갈래는 그림자 걸음·폭풍·빛의 가수다. 구역 이동은 같은 페이지 안 적재·해제 대신 저장 + 새로고침이다. 리플레이 입력은 스킬 명령 때문에 7바이트다.
- **발견**: '새 게임' 링크의 `?new=1`이 주소에 남아 새로고침마다 저장이 지워졌다. 지운 직후 주소에서 뺀다.
- **상세 기록**: 저장소 `docs/implementation-log.md`의 M3-C1 항목에 있다.

### M3-C2 — 고블린 궁수와 고블린 대장

**21번째 홀에 궁수 넷과 보스 고블린 대장을 넣었다.** 궁수는 0.8초 활을 당긴 뒤 쏜다. 화살은 기둥에 막히고 패링할 수 없다. 대장의 3연타는 패링할 수 있다. 돌진은 바닥의 붉은 띠로 예고되고, 벽에 박히면 휘청인다. 체력이 절반이 되면 휘파람으로 무리를 부른다. 북문 출구는 등불 셋과 대장 처치가 모두 필요하다. 테스트는 118개다.

- **발견**: 키네마틱 바디 위치는 물리 스텝 뒤에야 바뀐다. 그래서 돌진의 벽 충돌 판정이 늘 참이 됐고, 실제 이동량(보정된 속도)으로 바꿨다. 돌진 거리도 5.5m에서 9m로 늘렸다.
- **상세 기록**: 저장소 `docs/implementation-log.md`의 M3-C2 항목에 있다.

### M3-D — 장비와 전리품

**적이 금화와 장비를 떨어뜨리고, 6칸 · 5등급 장비를 장착하고, 밝힌 화로에서 미스릴로 강화한다.** M2에서 미뤄던 '빛의 도박' 전리품 등급도 이번에 넣었다. 최근 어둠에 머문 비율(지수 이동 평균)만큼 좋은 등급이 잘 나온다. 테스트는 125개다.

- **계획과 달라진 점**: 대장간 NPC 대신 밝힌 화로에서 강화한다. 엘프제/드워프제 등급은 '장인'으로 줄였다. 장착·강화는 입력 명령이라 리플레이가 재현한다. 저장은 v4다.
- **상세 기록**: 저장소 `docs/implementation-log.md`의 M3-D 항목에 있다.

### M3-E — 구역 3 마자르불의 방

**21번째 홀 북문 너머에 마자르불의 방을 넣었다.** 발린의 무덤에서 E를 누르면 방어전 3물결이 양옆 굴에서 쏟아지고, 막아 내면 북쪽 쇠문이 열린다. 방패를 든 우루크는 앞에서 온 약공격을 20%만 받는다. 강공격이나 패링 뒤 반격으로 방패를 깨거나, 옆·뒤를 쳐야 한다. 마자르불의 책 조각 3개(전체 12개 중)를 놓았다. 테스트는 136개이고 스모크는 23/23이다.

- **계획과 달라진 점**: 트롤은 이미 구역 1 보스라서, 구역 3의 절정은 방어전 마지막 물결(우루크 셋)이다. 퀘스트 엔진 대신 레벨 데이터와 전용 모듈로 만들었다. 저장은 v5(책 조각, 방어전 완료)다.
- **붕괴와의 연결**: 굴 입구의 금 간 기둥을 무너뜨려 봉쇄한 굴에서는 물결이 나오지 않는다. 한쪽만 지키는 전략이 된다.
- **상세 기록**: 저장소 `docs/implementation-log.md`의 M3-E 항목에 있다.

### M3-F — 구역 4 대장간과 깊은 탄갱

**마자르불의 방 북쪽 쇠문 너머에 두린의 대장간을 넣었다.** 용암 강을 돌다리 둘로 건너고, 떨어지면 그 자리에서 쓰러진다. 용암빛 때문에 다리 위에서는 건너편 궁수에게 잘 보인다. 발판 셋을 한꺼번에 눌러야 모루가 다시 타오르고 쇠문이 열린다. 횃불 둘을 발판에 내려놓고 마지막 발판에 서는 구조라, 빛을 내려놓아야 길이 열린다. 모루 앞은 우루크 대장(고블린 대장의 기술 + 이름)이 지킨다. 테스트는 142개이고 스모크는 23/23이다.

- **계획과 달라진 점**: 우루크 대장은 전용 외형 없이 고블린 대장을 이름만 바꿔 썼다. '전설 무기 제작' 사이드 퀘스트는 NPC와 함께 뒤로 미뤘다.
- **발견**: M3-E에서 방어전 쇠문을 수수께끼 문에서 빼는 수정이 실제로는 적용되지 않았다. 테스트가 문에서 14m 떨어진 곳에서만 확인해 놓쳤고, 이번에 고쳤다.
- **상세 기록**: 저장소 `docs/implementation-log.md`의 M3-F 항목에 있다.

### M4-B — 크하잣둠의 다리와 발로그전

**대장간 너머에 구역 5를 넣어, 새 게임부터 엔딩까지 한 번에 이어진다.** 1페이즈는 불의 벽이 5m/s로 다가오는 추격이다(질주를 섞어야 다리에 닿는다). 2페이즈는 다리 서쪽 단의 발로그와 싸운다. 내리찍기는 1.2초 예고되고, 피하면 칼이 박혀 가슴이 열릴 때만 피해가 다 들어간다(평소 25%). 날개 바람은 웅크려 버티고, 불덩이는 피한다. 3페이즈(체력 40%)에는 채찍(끌어당김)과 불의 고리(회피로 뚫기)가 더해진다. 체력 10%에서 더 내려가지 않고, 간달프가 다리를 내리쳐 발로그가 떨어진 뒤 동문으로 나가면 엔딩이다. 테스트는 151개이고 스모크는 23/23이다.

- **계획과 달라진 점**: '날개 뒤 약점'은 다리 위에서 뒤로 돌아갈 수 없어 '내리찍은 뒤 열린 가슴'으로 바꿨다. 탈출 QTE 대신 간달프 장면 뒤 동문까지 걸어 나간다. 발로그와 간달프는 에셋 없이 도형으로 짰다.
- **남은 것**: G2(새 게임부터 엔딩까지 버그 없이 완주)는 사람이 플레이해 확인해야 한다. 다리가 무너지는 연출과 리플레이 링크 공유(서버)도 남았다.
- **상세 기록**: 저장소 `docs/implementation-log.md`의 M4-B 항목에 있다.

### M3-G — NPC, 상점, 전설 무기, 책 조각 12개

**상인 노리(구역 2·4)와 대장장이 그로르(구역 4)를 넣었다.** 곁에서 E를 누르면 상점 창이 열린다. 상인은 예비 횛불·미스릴·장비 꾸러미를 팔고, 대장장이는 모루가 타오른 뒤 전설 무기 '두린의 도끼'를 벼리고 강화도 해 준다. 사고파는 것도 입력 명령이라 리플레이가 재현한다. 남은 책 조각 6개를 사이드 장소에 놓아 12개를 채웠고, 다 모으면 전설 장신구 '발린의 인장'을 받는다. 테스트는 155개이고 스모크는 23/23이다.

- **계획과 달라진 점**: 대화 분기·퀘스트 수주·데이터 퀘스트 엔진은 아직이다. 사이드는 책 조각 수집과 전설 제작으로 묶었다. NPC는 에셋 없이 도형으로 짰다.
- **상세 기록**: 저장소 `docs/implementation-log.md`의 M3-G 항목에 있다.

### M5-C — 출시 준비: 번들 분할, Lighthouse, 세계 연결 점검

**번들을 게임 코드와 라이브러리로 나눠(게임 204KB · three 1.0MB · Rapier 4.3MB, gzip 합계 약 2MB) 게임만 바뀐 배포에서 라이브러리를 캐시로 다시 쓴다.** Lighthouse(배포 빌드, WebGL2)는 접근성 100·권장 사항 100이다. 성능 41은 GPU 없는 환경에 모바일 4배 감속을 건 값이다. 가장 큰 요소가 부팅 끝에 나타나 부팅 전체(내비메시 굽기·셰이더 예열)가 잡혔다. 세계 연결 테스트는 구역 1에서 출구를 따라가면 엔딩에 닿는지, 모든 입구가 안전한지, 출구·화로로 걸어갈 수 있는지 확인한다. 테스트는 158개이고 스모크는 23/23이다.

- **계획과 달라진 점**: 구역 이동이 저장 + 새로고침이라 메모리 왕복 테스트는 필요 없었다. Rapier WASM 분리는 결정성 재검증이 필요해 미뤘다.
- **남은 것**: 실제 GPU·실기기 측정, G2 사람 완주, 내비메시 굽기 워커 이전, Cloudflare Pages 공개(계정 필요).
- **상세 기록**: 저장소 `docs/implementation-log.md`의 M5-C 항목에 있다.

### M5-D — 내비메시 굽기를 워커로

**부팅에서 가장 무거운 일인 내비메시 굽기(구역 하나 0.2\~0.8초)를 웹 워커로 옮겨, 캐릭터 파일 받기·Rapier·렌더러 준비와 겹친다.** 결과는 평범한 객체라 구조화 복제로 그대로 넘어오고, 테스트가 직접 구운 것과 해시가 같은지 본다. Lighthouse(모바일 4배 감속) 총 차단 시간은 5,300ms에서 2,840ms로 줄었다. 테스트는 159개이고 스모크는 23/23이다.

- **고른 길**: 빌드 때 미리 굽기는 구역 데이터를 빌드 스크립트에서 불러오는 도구가 더 필요하고 구역마다 JSON 0.5MB가 더해져 하지 않았다.
- **상세 기록**: 저장소 `docs/implementation-log.md`의 M5-D 항목에 있다.
